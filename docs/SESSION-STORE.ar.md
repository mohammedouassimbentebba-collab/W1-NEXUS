# مخزن الجلسة المرجعي SessionStore — W1-CIP v0.1

## 1. الغرض

`SessionStore` هو أول مكوّن تشغيلي دائم في التنفيذ المرجعي لـ`W1-CIP`. يحتفظ بالسجل الأصلي للجلسة كسلسلة غير قابلة للتعديل من أغلفة `ProtocolEnvelope`، ثم يبني منها فهارس قابلة لإعادة الإنشاء للوصول السريع إلى أحدث إصدارات الكيانات وآثار `ProtocolEvent` النشطة.

المصدر القانوني للحقيقة هو جدول الأحداث فقط. أما جداول الإسقاط فهي ذاكرة مشتقة يمكن حذفها وإعادة بنائها من السجل.

## 2. حدود هذه الخطوة

تنفذ هذه الخطوة:

- تخزينًا دائمًا محليًا باستخدام SQLite.
- قبول حدث واحد داخل معاملة ذرية.
- حجز `sequence` تحت قفل كتابة.
- تحقق JSON Schema والتحقق الدلالي وإعادة تشغيل السجل قبل القبول.
- جذر ثقة صريح لـ`recorded_by`.
- منع تعديل أو حذف صفوف الأحداث عبر Triggers.
- سلسلة SHA-256 تكشف التغيير في محتوى الحدث أو ترتيبه.
- فهارس للإصدارات وأحدث كيان وآثار البروتوكول النشطة.
- إعادة بناء الإسقاطات من الدفتر الأصلي.
- كشف الفجوات والتعارضات والعبث والتلف.
- كتابة متزامنة آمنة بين أكثر من عملية SQLite.

لا تنفذ بعد:

- توقيعًا رقميًا للأحداث.
- تخزينًا موزعًا أو إجماعًا بين عقد متعددة.
- نسخًا احتياطيًا خارجيًا أو تكرارًا جغرافيًا.
- تشفير الحقول الحساسة على مستوى التطبيق.
- تخزين ملفات الأدلة الثنائية نفسها؛ يحتفظ البروتوكول حاليًا بمراجعها المثبتة.
- Orchestrator أو موصلات مزودي النماذج.

## 3. قاعدة append-only

يخزن كل حدث في جدول `events` بمفتاح:

```text
(session_id, sequence)
```

ويفرض أيضًا:

```text
UNIQUE(session_id, message_id)
```

أضيف Triggerان يمنعان:

```text
UPDATE events
DELETE FROM events
```

التصحيح لا يتم بتغيير الصف القديم، بل بحدث جديد أو `ProtocolEvent` تعويضي وفق قواعد البروتوكول.

## 4. القبول الذري

تستعمل `append()` التسلسل التالي داخل `BEGIN IMMEDIATE`:

1. قراءة رأس الجلسة الحالي.
2. فحص إعادة الإرسال أو تعارض `message_id`.
3. تطبيق `expected_last_sequence` عند وجوده.
4. حجز رقم التسلسل التالي.
5. التحقق البنيوي من `ProtocolEnvelope`.
6. إعادة تشغيل السجل السابق مع الحدث المرشح.
7. رفض الحدث إذا ظهرت أي مخالفة.
8. حساب بصمة السلسلة.
9. إدخال الحدث.
10. تحديث الإسقاطات المشتقة.
11. تحديث رأس الجلسة.
12. تنفيذ `COMMIT`.

إذا فشلت أي خطوة ينفذ `ROLLBACK`، فلا يستهلك رقم تسلسل ولا تبقى فهارس جزئية.

## 5. جذر ثقة المسجل

لا يكفي أن يعلن الغلاف أن `recorded_by` هو Runtime موثوق. يجب أن يمرر مشغل المخزن قائمة محلية صريحة:

```python
trusted_recorders={
    ("runtime", "runtime-local-001"),
}
```

تخزن هذه القائمة محليًا في قاعدة البيانات، ولذلك يمكن إعادة فتح المخزن من دون تمريرها من جديد. لا يستطيع حدث بروتوكولي أن يضيف نفسه إلى جذر الثقة.

إذا كانت قاعدة البيانات جديدة ولم يحدد أي مسجل موثوق يرفض القبول بالرمز:

```text
session_store_trusted_recorder_not_configured
```

كما تطبق إعادة التشغيل قواعد:

- Bootstrap واحد فقط.
- Bootstrap هو الحدث الأول.
- عدم العمل قبل Bootstrap.
- `recorded_by` ضمن جذر الثقة.

## 6. التسلسل والتزامن

المخزن هو صاحب القرار النهائي في `sequence`.

يمكن للمتصل حذف الحقل وترك المخزن يضيفه:

```python
result = store.append(envelope_without_sequence)
```

ويمكن استعمال شرط تفاؤلي:

```python
result = store.append(
    envelope,
    expected_last_sequence=40,
)
```

إذا سبقت عملية أخرى الكاتب يصبح الشرط قديمًا ويرفض الحدث بـ:

```text
session_sequence_conflict
```

يستعمل SQLite قفل كتابة بين العمليات، ويستعمل الكائن `RLock` لحماية الاتصال المشترك بين الخيوط.

## 7. إعادة الإرسال الآمنة

إذا وصل `message_id` نفسه بالمحتوى القانوني نفسه، يعاد السجل السابق من دون إنشاء حدث جديد:

```python
result.already_present is True
```

إذا استعمل المعرف نفسه مع محتوى مختلف يرفض بـ:

```text
session_message_id_conflict
```

وبذلك يمكن للعميل إعادة المحاولة بعد انقطاع الشبكة من دون مضاعفة الأثر.

## 8. سلسلة التجزئة

يحسب كل حدث:

```text
event_hash = SHA256(bytes(previous_hash) + "\n" + canonical_json(envelope))
```

يبدأ أول حدث من:

```text
0000...0000  # 64 خانة
```

الترميز القانوني يستعمل:

- ترتيب المفاتيح.
- UTF-8.
- عدم استعمال `NaN`.
- عدم إضافة مسافات غير دلالية.

تكشف `verify_integrity()`:

- تعديل JSON المخزن.
- تغيير `message_id` أو `sequence`.
- تغيير `previous_hash` أو `event_hash`.
- اختلاف رأس الجلسة.
- اختلاف الإسقاطات عن نتيجة إعادة التشغيل.

هذه السلسلة تكشف العبث، لكنها ليست توقيعًا رقميًا؛ من يملك صلاحية كاملة على قاعدة البيانات والبرنامج يستطيع إعادة حساب السلسلة. التوقيع ومفاتيح الحماية مرحلة لاحقة.

## 9. الجداول

### `sessions`

يحفظ رأس كل جلسة:

```text
last_sequence
last_recorded_at
last_event_hash
```

### `events`

الدفتر غير القابل للتعديل، ويحتوي الغلاف القانوني الكامل وبصمتي السابق والحالي.

### `entity_versions`

فهرس قابل لإعادة البناء لكل `VersionedEntity` مقبول.

### `latest_entities`

يشير إلى أحدث إصدار لكل هوية كيان.

### `protocol_effects`

يعرض آثار `ProtocolEvent` النشطة والمعوضة، لكنه ليس مصدر الحقيقة.

### `trusted_recorders`

جذر الثقة المحلي للمسجلين.

## 10. إعادة التشغيل والتعافي

```python
state = store.replay(session_id)
```

تعيد الحالة الحتمية من الدفتر.

إذا تلفت الفهارس المشتقة يمكن تشغيل:

```python
store.rebuild_projections(session_id)
```

وتحذف الإسقاطات ثم تبنيها مجددًا داخل معاملة واحدة.

الفشل أثناء الكتابة لا يترك نصف حدث لأن SQLite يعيد المعاملة غير المكتملة عند فتح قاعدة البيانات بعد الانقطاع.

## 11. الاستعلامات الأساسية

```python
store.get_events(session_id)
store.get_event(session_id, message_id)
store.get_entity(session_id, "decision", decision_id)
store.get_entity(session_id, "decision", decision_id, 3)
store.get_active_protocol_effects(session_id)
store.get_summary(session_id)
store.list_sessions()
store.verify_integrity(session_id)
```

## 12. الاعتمادات بالـApproval

وسع محرك إعادة التشغيل ليسجل الموافقات ذات الاستعمال الواحد داخل:

```text
consumed_approvals
```

وعندما يستعمل غلاف `authorized_by` من نوع `approval` يتحقق من:

- كون الموافقة أحدث إصدار وفعالة.
- مطابقة المستفيد الفعلي.
- مطابقة العملية والهدف المثبت.
- عدم انتهاء الصلاحية.
- عدم استهلاكها سابقًا.

## 13. سياسة الدفعات

`append_many()` أداة تسلسلية مريحة، لكن حد المعاملة البروتوكولي في `v0.1` هو **غلاف واحد**. لذلك لا تدعي الدالة أن مجموعة اعتباطية من الأحداث إما تقبل كلها أو ترفض كلها.

إذا احتاج Orchestrator لاحقًا إلى معاملة متعددة الأحداث فستحتاج دلالة بروتوكولية صريحة للدفعة، وليس مجرد معاملة قاعدة بيانات خفية.

## 14. الضمانات الحالية

يوفر التنفيذ الحالي:

```text
Durability محلية
Atomic append
Writer serialization
Optimistic concurrency
Idempotent retry
Tamper evidence
Deterministic replay
Rebuildable projections
```

ولا يدعي بعد:

```text
Distributed consensus
Cryptographic authorship
External disaster recovery
Exactly-once provider execution
```
