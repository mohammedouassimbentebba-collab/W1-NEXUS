# رؤية W1 Nexus

## 1. المشكلة

تستطيع النماذج والوكلاء اليوم توليد الإجابات، استخدام الأدوات، وتنفيذ بعض المهام داخل التطبيقات. لكن جمع عدة نماذج في جلسة واحدة لا يضمن نتيجة أفضل؛ فقد يكرر كل منها أخطاء الآخر، أو تتضخم التكلفة، أو يضيع الهدف الأصلي، أو يصعب معرفة مصدر القرار النهائي.

المشكلة التي يعالجها W1 Nexus ليست مجرد نقل الرسائل بين الوكلاء، بل تنظيم العمل المشترك بحيث تكون النتيجة قابلة للفحص والمراجعة.

## 2. الرؤية

> **الهدف التطويري الرسمي هو W1 Nexus الكاملة، وليس الاكتفاء بنسخة MVP.** تستخدم الإصدارات المرحلية للتحقق من المعمارية، لكنها لا تمثل نقطة التوقف النهائية.

يسعى W1 Nexus إلى توفير منظومة يستطيع داخلها فريق غير متجانس من النماذج والوكلاء أن:

- يفهم هدف المستخدم ضمن عقد صريح.
- يوزع العمل بحسب القدرات والقيود.
- يعمل على حالة مشتركة للمهام والملفات والتطبيقات.
- يفصل الحلول المستقلة قبل المقارنة لتقليل التأثر المتبادل.
- يربط الادعاءات بالأدلة والافتراضات.
- يسجل الاعتراضات الحرجة ويمنع إخفاءها داخل الصياغة النهائية.
- ينفذ الأفعال ضمن صلاحيات قابلة للتدقيق والتراجع.
- يعرف متى يتوقف ومتى يطلب قرار المستخدم.

## 3. ما ليس عليه المشروع

W1 Nexus ليس:

- غرفة دردشة لعدة نماذج.
- مزود نماذج جديدًا.
- بديلًا شاملًا لـMCP أو A2A أو واجهات التطبيقات.
- ادعاءً بأن إجماع النماذج يساوي الحقيقة.
- نظامًا يمنح الوكلاء صلاحيات غير محدودة.

## 4. البنية المعمارية

```text
W1 Nexus
├── W1-CIP Core
├── Protocol Extensions
│   ├── Action
│   ├── Scientific
│   ├── Advanced Review
│   └── Human Approval
├── Runtime Components
│   ├── Orchestrator
│   ├── Action Runtime
│   ├── Evidence Store
│   ├── Long-Term Memory + Knowledge Fabric
│   └── Verification Engine
└── Products
    ├── Nexus Workspace
    ├── SDK
    └── CLI
```

### W1-CIP

يحدد لغة التعاون وقواعده: الهوية، الهدف، المهام، المساهمات، الأدلة، الاعتراضات، المراجعات، الموافقات، الحالات، والنتيجة.

### W1 Action Runtime

ينفذ القرارات داخل الأنظمة والتطبيقات. يفضل الوسائل المنظمة متى توفرت، وفق ترتيب مبدئي:

1. API رسمي.
2. MCP أو أداة منظمة مماثلة.
3. إضافة أو برنامج نصي داخل التطبيق.
4. تحكم مباشر في الواجهة الرسومية.
5. تدخل المستخدم.

اختيار الوسيلة قرار تشغيلي، وليس جزءًا ثابتًا من جوهر البروتوكول.

### W1 Scientific Loop

امتداد اختياري للمسائل البحثية والهندسية. يضيف الفرضية والتوقع والتفنيد والتجربة والملاحظة وعدم اليقين والتكرار.

### W1 Nexus Workspace

تطبيق مرجعي يتيح للمستخدم رؤية الهدف، رسم المهام، أعضاء الفريق، الأدلة، الاعتراضات، الأذونات، حالة التطبيقات، وسجل القرارات.

### W1 Long-Term Memory + Knowledge Fabric

يحفظ الحقائق والقرارات والتفضيلات والإجراءات عبر الجلسات مع مصدر وصلاحية وACL وفصل بين المشاريع. لا يسمح بتحويل استنتاجات النماذج إلى ذاكرة دائمة تلقائيًا، ولا يحسم التعارضات أو يخلط المشاريع بصورة صامتة.

## 5. مبادئ التصميم

### نواة صغيرة وإضافات اختيارية

لا ينبغي أن تتحمل التطبيقات البسيطة وظائف علمية أو تشغيلية لا تحتاج إليها.

### الحالة قبل المحادثة

الهدف والمهام والأدلة والملفات والقرارات كيانات منظمة، وليست معلومات مدفونة في سجل رسائل طويل.

### دليل أقوى من التصويت

لا يحسم القرار بعدد النماذج المؤيدة وحده. تؤخذ في الحسبان جودة الدليل، استقلال المصدر، ملاءمة التخصص، نتيجة الاختبار، وعدم اليقين.

### سلطة قرار صريحة

لا يملك المنظم حق اعتماد كل قرار لمجرد أنه يدير الجلسة. يحدد عقد الهدف أو خطة الفريق صاحب الصلاحية لكل فئة من القرارات، وشروط المراجعة والتصعيد وإمكان التراجع.

### أقل صلاحية لازمة

كل وكيل يحصل على أقل قدر من الصلاحية يكفي لمهمته. ويملك وكيل واحد فقط حق تعديل المورد نفسه في اللحظة نفسها.

### أقل سياق لازم

لا يطّلع الوكيل إلا على السياق المرتبط بمهمته والغرض المصرح به، ضمن منحة محددة النطاق والمدة وقواعد إعادة المشاركة.

### الإنسان صاحب القرار النهائي

تتطلب الأفعال غير القابلة للتراجع، أو عالية المخاطر، أو المتجاوزة للعقد موافقة صريحة.

### قابلية التدقيق وإعادة الإنتاج

ينبغي أن نتمكن من معرفة من اقترح القرار، وما الذي دعمه، ومن راجعه، وما الذي تغير، وهل يمكن إعادة النتيجة.

ترد القواعد المعيارية لهذه المبادئ في [نموذج حوكمة W1-CIP](GOVERNANCE.ar.md).

## 6. فرضيات تحتاج إلى اختبار

هذه نقاط بحثية، وليست حقائق محسومة:

- أن الاعتراض المنظم يحسن الجودة أكثر من المراجعة الحرة.
- أن العزل المؤقت للمقترحات يقلل الاتفاق الجماعي الخاطئ.
- أن اختيار الفريق بحسب المخاطر يخفض التكلفة من دون إضعاف النتيجة.
- أن سجل الأدلة والقرارات يمكن أن يبقى مفيدًا من دون أن يصبح عبئًا تشغيليًا.
- أن المخطط المشترك يعمل مع مزودين وأطر مختلفة من دون فقد معلومات مهمة.

يجب تقييم هذه الفرضيات بتجارب ومقاييس واضحة خلال تطوير النماذج الأولية.

## 7. معيار النجاح

ينجح المشروع عندما يثبت، في مهام قابلة للقياس، أنه يحسن واحدًا أو أكثر من الجوانب الآتية مقارنة بخط أساس واضح:

- صحة النتيجة.
- اكتشاف الأخطاء الحرجة.
- قابلية التتبع.
- قابلية إعادة الإنتاج.
- تكلفة الوصول إلى نتيجة مقبولة.
- الوقت اللازم للوصول إليها.
- دقة الالتزام بقيود المستخدم وصلاحياته.


## مبدأ Local-First Multi-Model

لا تعتمد W1 Nexus على نموذج واحد أو على خوادم مركزية تابعة للمشروع. يختار المستخدم أو الفريق مجموعة من أفضل النماذج التي يفضلونها، ويمكن توزيعها على التنفيذ والتخصص والمراجعة والتحقق والتركيب.

يجب أن تظل النواة قابلة للعمل عبر:

- نماذج مفتوحة الأوزان محليًا.
- مفاتيح API يملكها المستخدم.
- حسابات أو Brokers رسمية عندما يسمح المزود بذلك.
- نماذج خاصة داخل الشركات.
- Plugins وتطبيقات خارجية.
- تضمين W1 داخل منتج آخر عبر SDK أو API محلية.

الخدمات السحابية المستقبلية اختيارية، ولا تصبح شرطًا لاستعمال البروتوكول أو Runtime.
