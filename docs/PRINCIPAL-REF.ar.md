# PrincipalRef — W1-CIP v0.1

## 1. الغرض

يعرّف `PrincipalRef` هوية طرف يمكن أن يظهر بصفته فاعلًا أو طرفًا ممثَّلًا أو مكوّنًا مسجلًا داخل جلسة `W1-CIP`.

هذا المرجع يجيب عن سؤال **من هو الطرف؟** فقط. ولا يثبت وحده:

- امتلاك الدور أو الصلاحية.
- صحة الهوية تشفيريًا.
- القدرات أو الأدوات.
- الثقة بالمكوّن.
- الإذن بالتصرف نيابة عن طرف آخر.

تثبت السلطة عبر `authorized_by`، وتثبت القدرات والسياسات في كيانات مثل `AgentCard` و`RoleAssignment` و`Approval`.

## 2. معيار المخطط

يستخدم المخطط JSON Schema Draft 2020-12.

معرّف المخطط:

```text
urn:w1-cip:schema:0.1:principal-ref
```

البنية القانونية الدنيا:

```yaml
principal_type: agent
principal_id: agent-electronics-01
```

لا يقبل المخطط خصائص إضافية.

## 3. أنواع الأطراف

القيم المسموحة لـ`principal_type` هي:

| النوع | الدلالة |
|---|---|
| `agent` | وكيل ذكاء اصطناعي أو منفذ نموذجي مسجل للجلسة |
| `human` | إنسان مشارك، ويستحسن استعمال معرف جلسي مستعار بدل اسم أو بريد مباشر |
| `runtime` | حدود البروتوكول الموثوقة التي تستقبل وتتحقق وتسجل الأحداث |
| `service` | مكوّن برمجي مستقل مثل المنظم أو مراقب أمني، لكنه ليس سجل البروتوكول نفسه |
| `tool` | أداة يمكن نسبة فعل مباشر إليها، مثل حاسبة أو منفذ اختبار |

لا يحدد النوع دور الطرف. فقد يكون `agent` منفذًا أو مراجعًا أو متحققًا بحسب `RoleAssignment`، وقد تحمل خدمة دورًا تشغيليًا من دون أن تكون سلطة قرار.

## 4. مساحة الهوية

تكون هوية الطرف فريدة داخل:

```text
session_id + principal_type + principal_id
```

يجب أن يكون `principal_id` بصيغة lowercase وفق نمط المعرفات المعياري. ولا يعاد استعمال الهوية داخل الجلسة لطرف مختلف.

`PrincipalRef` غير مصدّر عمدًا. فهو يشير إلى هوية مستقرة، بينما تحفظ البيانات القابلة للتغير—مثل قدرات الوكيل أو سياسة الخدمة—داخل كيانات مصدّرة منفصلة. إذا تغيرت بطاقة وكيل، يبقى `PrincipalRef` نفسه وتثبت العملية الإصدار الملائم من `AgentCard` عند الحاجة.

## 5. استعماله داخل ProtocolEnvelope

- `actor`: الطرف الذي قدم الفعل إلى حدود البروتوكول أو نفذه مباشرة.
- `on_behalf_of`: الطرف الأصلي الذي يمثله `actor`، ولا يظهر إلا عند وجود تمثيل حقيقي.
- `recorded_by`: Runtime موثوق قبل الحدث وثبته في السجل.

أمثلة:

```yaml
actor:
  principal_type: agent
  principal_id: agent-electronics-01
```

```yaml
actor:
  principal_type: service
  principal_id: orchestrator-01
on_behalf_of:
  principal_type: agent
  principal_id: agent-electronics-01
```

```yaml
recorded_by:
  principal_type: runtime
  principal_id: orchestrator-runtime-01
```

لا يجوز أن يساوي `on_behalf_of` قيمة `actor`؛ فوجوده عندئذ زائد ومضلل.

## 6. الطرف الفعلي للصلاحية

لأغراض مطابقة `authorized_by`:

```text
إذا وجد on_behalf_of → الطرف الفعلي هو on_behalf_of
وإلا → الطرف الفعلي هو actor
```

تثبت طبقة الجلسة الآن أن `RoleAssignment` المشار إليه في `authorized_by` يمنح النطاق المطلوب للطرف الفعلي عبر قراءة حمولة [RoleAssignment](ROLE-ASSIGNMENT.ar.md). وأصبح التحقق من `Approval` يثبت العملية الدقيقة والهدف والطرف والمدة وعدم الاستهلاك السابق. لا يستطيع `PrincipalRef` وحده إثبات السلطة.

`recorded_by` ليس الطرف الفعلي للصلاحية ولا يكتسب سلطة الفعل لمجرد تسجيله.

## 7. حدث تأسيس الجلسة

في `session.bootstrap.completed` يجب أن يكون كل من `actor` و`recorded_by` مرجع Runtime نفسه، لأن Runtime المحلي الموثوق هو الذي أنشأ وسجل واقعة التأسيس. أما مالك الجلسة البشري فيظهر بوصفه `subject` داخل حمولة `RoleAssignment` الأول، ولا يصبح Runtime مالكًا بسبب التسجيل.

## 8. ما يفرضه المخطط وما يبقى دلاليًا

يفرض JSON Schema:

- وجود `principal_type` و`principal_id`.
- الأنواع الخمسة المسموحة.
- صيغة المعرف lowercase.
- منع الخصائص غير المعروفة.
- كون `recorded_by` من النوع `runtime` داخل `ProtocolEnvelope`.
- كون `actor` في حدث التأسيس من النوع `runtime`.

وتفرض طبقة الدلالة أو حالة الجلسة:

- اختلاف `actor` و`on_behalf_of`.
- تطابق `actor` و`recorded_by` في حدث التأسيس.
- ثقة المضيف بـ`recorded_by` لكل حدث.
- فردية هوية الطرف داخل الجلسة.
- مطابقة سند الصلاحية للطرف الفعلي ونطاق العملية.

## 9. أمثلة الاختبار
