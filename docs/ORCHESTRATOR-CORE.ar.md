# Orchestrator Core — التنفيذ المرجعي

## الغرض

`OrchestratorCore` هو أول محرك تشغيل فعلي فوق عقود `W1-CIP` و`SessionStore`. وظيفته ليست كتابة الإجابة بدل الوكلاء، بل تنظيم دورة العمل بطريقة حتمية وقابلة للاستئناف:

1. قراءة `GoalContract` و`TeamPlan` و`ExecutionResourcePlan` المقبولة.
2. تحويل الهدف إلى رسم مهام مجرد.
3. تحديد المهمة الجاهزة بحسب الاعتماديات.
4. اختيار المورد وفق الدور والمرحلة والخطر والتعقيد والحصة.
5. منح أقل قدر مطلوب من السياق.
6. استدعاء موصل المزود بمفتاح idempotency ثابت.
7. قبول المخرجات المطابقة للعقد فقط.
8. تسجيل الحصة المستهلكة والتحويل إلى بديل عند الحاجة.
9. فرض المراجعة الإضافية إذا كان البديل أضعف من المورد الأساسي.
10. استكمال `verification → review → decision/approval → synthesis`.

## المكونات

### GoalTaskCompiler

يبني رسمًا مجردًا يتضمن بحسب عقد الهدف:

- مهمة تنفيذ لكل مخرج مطلوب.
- جمع دليل وتحقق لكل معيار نجاح قابل للتحقق.
- مراجعة مستقلة عند الخطر المتوسط/العالي أو التكلفة المادية أو وجود قرار.
- مهمة قرار لكل مخرج من نوع `decision`.
- موافقة عندما يطلب العقد إشرافًا بشريًا.
- مهمة `synthesis` تنتج `final_result`.

المترجم لا ينشئ أحداث `Task` القانونية بنفسه؛ بل يصف نية العمل. تحويل هذه النيات إلى كيانات `Task` و`ContextGrant` و`Contribution` الفعلية مسؤولية `EnvelopeFactory` الخاصة بحزمة المجال.

### TeamPlanner

يستنتج الأدوار المطلوبة ويختار إسنادًا متاحًا لكل دور. يعيد الأدوار الناقصة صراحة، ولا يعوض المراجع أو المتحقق بنموذج منفذ واحد.

### ProviderAdapter

واجهة المزود صغيرة عمدًا:

```python
class ProviderAdapter(Protocol):
    resource_id: str
    supports_idempotency: bool

    def invoke(self, request: ProviderRequest) -> ProviderResponse:
        ...
```

يجب على الموصل الحي أن يميز بين:

- `ProviderQuotaExhausted`
- `ProviderTransientError`
- `ProviderPermanentError`
- `ProviderOutcomeUncertain`

### OrchestratorJournal

مخزن تشغيلي mutable منفصل عن دفتر البروتوكول append-only. يسجل:

- حالة التشغيل.
- حالة كل مهمة.
- محاولات المزود.
- مفاتيح idempotency.
- الردود المكتملة.
- نسخة خطة الموارد بعد الخصم أو نفاد الحصة.

هذا الفصل مقصود: سجل البروتوكول هو الحقيقة القانونية، بينما Journal نقطة استئناف تشغيلية قابلة للإصلاح.

## الحصص والتحويل

عندما يبلغ المزود عن نفاد الحصة:

1. تسجل المحاولة كفاشلة بسبب الحصة.
2. تصبح حصة المورد `exhausted` و`remaining_units = 0`.
3. إذا كان المورد نشطًا في قاعدة توجيه، تنتقل القاعدة إلى أول بديل صالح.
4. يسجل الإفصاح عن المورد الأصلي والبديل وسبب التحويل.
5. إذا لم يوجد بديل آمن تصبح الحالة `awaiting_reset` أو `awaiting_user` أو `blocked` وفق السياسة.

لا يسمح لخطة محدثة أن تبقي `active_resource_id` مشيرًا إلى مورد منهك.

## تفاوت القوة

يستعمل المحرك `route_execution_resource()`، ولذلك:

- لا يوجد تصويت عددي بين النماذج.
- درجة الملاءمة خاصة بالمهمة.
- لا يحدث downgrade بصمت.
- البديل الأضعف قد يفرض مراجعة إضافية.
- لا يكتمل التشغيل إذا كانت المراجعة الإضافية المطلوبة غير موجودة في رسم المهام.

## تقليل السياق

يحصل كل مزود على الحقول الموجودة فقط في:

```python
CompiledTask.required_context_fields
```

ويُرفض الرد إذا أعلن استعمال حقل لم يُمنح له:

```text
orchestrator_undeclared_context_used
```

القيم الحساسة غير المطلوبة لا تدخل `ProviderRequest`.

## الاستئناف وExactly-once

الحالات التالية توقف قابل للاستئناف وليست نهاية دائمة:

```text
blocked
awaiting_reset
awaiting_user
```

عند إعادة التشغيل بالـ`run_id` نفسه بعد تحديث الحصة أو السياق، تعود المهمة المتوقفة إلى `pending`، بينما تبقى المهام المكتملة محفوظة ولا تستدعى مجددًا. أما `awaiting_reconciliation` فتحتاج مصالحة صريحة لأنها قد تمثل أثرًا خارجيًا مجهول النتيجة.

لكل محاولة مفتاح ثابت مشتق من:

```text
run_id + task_id + resource_id + attempt
```

- إذا كانت الاستجابة محفوظة، يعاد استعمالها من Journal.
- إذا كانت المحاولة معلقة وكان المزود يدعم idempotency، يمكن تكرار الطلب بالمفتاح نفسه.
- إذا كانت النتيجة مجهولة والمزود لا يدعم idempotency، يتوقف التشغيل عند:

```text
awaiting_reconciliation
```

ولا يكرر الإجراء بصورة قد تنتج أثرًا مزدوجًا.

## EnvelopeFactory

المحرك لا يفترض شكلًا واحدًا لبناء كيانات المجال. تستقبل `EnvelopeFactory` أحداث التشغيل وتعيد صفرًا أو أكثر من `ProtocolEnvelope`.

المضمن `ArtifactEnvelopeFactory` مخصص للاختبارات والعرض فقط؛ فهو يحول أثر التشغيل إلى `artifact` عامة. حزمة الإنتاج يجب أن تحول الأحداث إلى الكيانات المعيارية المناسبة مثل:

- `Task`
- `ContextGrant`
- `Contribution`
- `Evidence`
- `Verification`
- `Review`
- `Approval`
- `Decision`
- `FinalResult`

كما يستطيع `ProviderResponse.protocol_envelopes` حمل أغلفة معيارية جاهزة؛ يقبلها المحرك عبر `SessionStore` بعد التحقق الكامل.

## الحدود الحالية

لم تنفذ بعد:

- موصلات حية لـOpenAI أو Anthropic أو Google.
- اكتشاف الحصص آليًا من واجهات المزودين.
- مولد عام يحول كل `CompiledTask` إلى كيان `Task` قانوني دون حزمة مجال.
- جدولة مهام متوازية.
- إلغاء طلب حي قيد التنفيذ.
- قياس التوكنات والتكلفة المالية من المزود الحقيقي.
- Exactly-once لمزود لا يقدم idempotency.

هذه الحدود لا تمنع تشغيل المرجع الحتمي بالموصلات المكتوبة أو المزود البرمجي `ScriptedProvider`.


## التكامل مع Provider Connectors

تنفذ طبقة [Provider Connectors](PROVIDER-CONNECTORS.ar.md) موصلات السحابة والمحلي. تحفظ الاستجابات الموحدة في Journal التشغيلية، وتسجل ملاحظات الحدود في `provider_quota_observations`. يعامل المنظم `ProviderRateLimited` كحد متجدد يسمح بالتحويل إلى بديل، ولا يساويه بـ`ProviderQuotaExhausted`.


## التكامل مع Long-Term Memory

يستطيع `OrchestratorCore` استقبال `memory_context_provider`. يطلب منه فقط الحقول الموجودة في `required_context_fields` وغير الموجودة في السياق الحالي. لا تستطيع الذاكرة تجاوز قيمة قدمها المستخدم في التشغيل الحالي.

إذا وجد سجل واحد نشط وغير متعارض ومصرح به، يضاف الحقل مع Citation في حدث `orchestrator.context.granted`. إذا كان الحقل مفقودًا يبقى التشغيل عند `awaiting_user`، وإذا كان متعارضًا يتوقف بخطأ `orchestrator_memory_conflict` بدل اختيار قيمة تلقائيًا.
